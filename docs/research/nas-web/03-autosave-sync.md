# 自动保存与多设备同步设计

用户要求：定时自动保存前端编辑进度，避免没有主动提交后端导致丢稿。本章将该要求作为首版必做项。以下参数是建议默认值，需经真实设备测试调整，并非现有功能。

## 保存触发

| 层次 | 默认触发 | 目的 |
| --- | --- | --- |
| 本机草稿 | 输入变化后约 300ms 合并写 IndexedDB | 短暂断网、刷新或崩溃恢复 |
| 停止输入保存 | 约 1.5 秒无新输入，且文档 dirty | 正常写作及时提交 NAS |
| 周期兜底保存 | 页面活跃且 dirty 时，每 10 秒检查 | 持续输入时仍提交，不被防抖无限推迟 |
| 主动保存 | Ctrl/Cmd+S 或保存按钮 | 用户明确要求立即保存 |
| 场景触发 | 切章节、切作品、路由离开、网络恢复、页面重新可见 | 尽快冲刷待提交内容 |
| 页面隐藏 | 尝试提交，并保留本机草稿 | 尽力处理；不承诺浏览器会完成网络请求 |

定时器仅在已登录、文档可编辑且存在变化时工作。只读修稿、已确认的定稿等必须遵守原有生命周期；不能为自动保存绕过“重新起草/解锁”等明确操作。恢复候选只保存候选本身，不自动提升为正式草稿。

中文组合输入期间不替换编辑器内容、不移动光标，compositionend 后调度提交。可在本地保留输入快照；必须测试真实中文输入法，不只测试键盘事件模拟。

浏览器被系统强杀可能来不及完成最近一次本地写入，后台定时器也可能暂停。因此不承诺零字符损失；目标是正常前台操作下将未落盘窗口压至本地合并周期，并如实显示保存状态。

## 状态模型

```text
clean → dirty/local_pending → local_saved → saving → synced
                                 ↑           ├→ offline/retry
                                 └───────────┤
                                             ├→ conflict
                                             └→ storage_error
```

只有服务器事务提交并返回匹配快照的确认，才显示“已保存到 NAS”。本地 IndexedDB 写成功可以显示“已保存到本机，等待同步”；尚未写成功不能显示。显示最近 NAS 保存时间和待保存状态，磁盘满、配额耗尽、登录失效必须明显提示。

UI 偏好如光标、滚动位置、打开章节与正文分开存储；光标/滚动位置建议按设备保存，避免电脑的位置覆盖手机位置。

## 客户端保存队列

每个文档最多一个在途保存请求。请求冻结内容快照、baseRevision、mutationId、editorSessionId 和 localSequence。请求期间继续输入只更新本地最新版本；收到旧快照确认后，不能清除新内容的 dirty 标记。

收到成功确认后更新服务器 revision，立即调度尚未提交的新快照。对于结果未知的超时，同一 mutationId、同一请求体重试；若内容已改变，必须用新 mutationId。网络恢复先确认未知提交结果，或以同一幂等请求重试，不盲目创建第二次写入。

本地草稿键包含用户、项目、文档和编辑会话，避免多标签覆盖。存储 baseRevision、baseContentHash、localSequence、内容、更新时间和提交收据。BroadcastChannel 可提示同机重复编辑，但服务端 CAS 才是最终保障。

重试采用指数退避加抖动；冲突、鉴权失败、校验失败不无限重试。退出登录保留待同步稿件时需明确提醒，隔离账户并按用户选择处理敏感草稿。

## 服务端原子保存

示意请求：

```json
{
  "baseRevision": 37,
  "mutationId": "uuid",
  "editorSessionId": "uuid",
  "localSequence": 102,
  "content": "正文快照"
}
```

在项目数据库的单个事务中：

1. 验证身份、作品归属、文档可编辑状态及大小限制。
2. 查询 mutationId 收据；相同键且相同请求摘要返回原结果，不同摘要拒绝。
3. 校验 baseRevision 与当前编辑修订一致，不一致返回 409，保留双方文本。
4. 调用领域写入服务，执行内容/来源约束；更新正文及编辑 revision。
5. 同事务保存幂等收据和文档变更事件，提交后返回 revision、内容 hash、保存时间。

幂等收据保留期应覆盖离线重试窗口；收据过期后仍由 baseRevision 防止重复覆盖，必要时读取当前 hash 确认。不能把原有“稿件第几版”的 version 当作高频保存计数。

所有会改变该文档内容的路径，包括手工保存、AI 应用、历史恢复、导入替换和管理员操作，都必须推进同一修订标记；只给自动保存接口增加 revision 仍会漏掉冲突。

## 多设备冲突

设备 A 和 B 均读到 revision 37；A 保存成功变成 38；B 的 37 提交返回冲突。B 本地内容仍可读、可导出，并显示服务器稿与本机稿。首版由用户对比决定，禁止以最后写入时间或设备时钟自动覆盖。

恢复页面时同时读本地稿与服务端版本：基线未变化可继续同步；已经变化则进入恢复/冲突界面。不要在首次挂载时用服务器文本覆盖尚未同步的本地草稿。

AI 结果绑定启动时的内容版本/hash。期间用户编辑，AI 结果保存为候选，应用前重新校验；不得覆盖自动保存的新内容。

## 历史与空间管理

结合 Reveric 保存队列和字段级变更记录的调研，进一步区分 editRevision（并发控制）、historyCheckpoint（用户历史）与 domainVersion（稿件业务版本）。详见 [整合优化](05-reveric-integration.md)。保留本方案默认触发参数，不能将本地应用的 800ms 保存机制当作网络同步保障。

高频自动保存不必每次生成用户可见的“新稿”。编辑 revision 用于并发；历史检查点可每 5 分钟有变化时、切换章节时、AI 应用前和手动保存时生成，最终策略需符合原有草稿历史模型。历史清理不得删除定稿、用户明确保留版本和冲突副本。

本地稿清理需已获得服务端确认，且没有更新的 localSequence。配额不足时显示错误并提供复制/下载，不能吞掉异常。备份策略与浏览器本地缓存独立。

## 必须通过的验收

- 持续输入 60 秒，周期保存确实执行；停止输入后防抖提交。
- 第一次保存尚未返回时继续输入，旧确认不清除新内容 dirty 状态。
- 服务端已保存但响应丢失，重试不会重复生成业务版本。
- 两设备同章同时保存，旧稿被拒绝，双方内容可找回。
- 断网编辑后刷新、重新登录、重启浏览器，按实际存储保留情况恢复并处理冲突。
- 手机切后台再回到页面，恢复本地稿并同步，不依赖后台定时器。
- 中文 IME、粘贴长文本、撤销重做不跳光标、不丢字。
- IndexedDB 失败、NAS 磁盘满、401、409、500 均不显示“已保存到 NAS”。
- 切换项目时在途响应不会写进新项目；多标签本地键不会互相覆盖。
